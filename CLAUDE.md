# Конституция проекта

Документ для AI-агентов и людей. Любой новый чат начинает работу с прочтения этой конституции. Правки — только от владельца. Агент конституцию не редактирует, но может предложить изменение отдельным сообщением.

---

## 0. Стек по умолчанию

- **Хостинг:** Vercel
- **БД:** Neon (Postgres)
- **Язык:** TypeScript
- **AI:** AIMLAPI (раздел 4)

Можно отойти от стека при необходимости — это архитектурное решение → агент спрашивает (раздел 7).

---

## 1. Схема БД — без ручных шагов

- **Самопровижининг и идемпотентность.** На чистой БД приложение поднимается само: либо `CREATE TABLE IF NOT EXISTS` при первом обращении (кэш и вспомогательные таблицы), либо миграции, запускаемые автоматически на деплое/старте. Ручной SQL = баг процесса.
- **Один источник правды на таблицу.** Либо ORM-схема, либо ленивый `CREATE` — не оба.
- **Обязательное поле во всех таблицах:** `created_at` (`timestamptz`, default `now()`). Нужно для безопасной очистки тестовых данных (раздел 6).
- **Громко vs тихо:**
  - **Тихо** (`try/catch` + лог в `app_errors`): провал создания вспомогательной таблицы, неважные данные, провал записи лога самого по себе.
  - **Громко** (исключение, приложение падает на старте): read-only токен БД, упала миграция core-таблицы, отсутствуют обязательные env. Молчать здесь нельзя.

## 2. Диагностика — один адрес для всего

Любой агент начинает разбор отсюда. Имена зафиксированы и не меняются.

- **`app_errors`** — единственная таблица для логов. Бэкенд и клиент в одном формате: `ts`, `level`, `source` (`server` \| `client`), `route`, `message`, `stack`, `build`, `user_agent`, `meta`.
- **`GET /api/admin/errors?limit=N`** — дамп последних ошибок.
- **`/admin`** — защищённая страница (простой токен из env Vercel). Содержит:
  - Структуру БД: таблицы и колонки с описаниями на русском (из реестра/комментариев схемы).
  - Просмотр строк постранично, read-only по умолчанию.
  - Дамп `app_errors`.
  - Результаты прогонов юнит-тестов (раздел 8).
- Пользователю наружу: понятное сообщение + `error_id` для поиска в `app_errors`. Стандартная форма API-ошибки: `{ error: { code, message, error_id } }`.

## 3. UX Kit — кит вперёд фичей

- В начале каждого проекта собирается UX Kit: палитра, типографика, базовые компоненты (`Button`, `Input`, `Card`, `Modal`, `Form`, `Toast`). Живёт в `src/components/ui/`.
- Дальше во всех разделах используем готовое. Новый компонент — только если существующего реально нет.
- Глобальные CSS-классы не плодим.
- Изменение UX Kit (добавление/правка базового компонента) = архитектурное решение → агент спрашивает.

---

## 4. AI-модели — только через AIMLAPI

- OpenAI-совместимый шлюз: `https://api.aimlapi.com/v1`. Один ключ на все модели (GPT, Claude, Gemini, Perplexity).
- **Канонический env: `AIMLAPI_KEY`.**
- Отдельных ключей OpenAI/Anthropic/Perplexity не заводим.
- **Качество > экономия.** Продукты для личного использования, на токенах не экономим. Брать модель с максимальной вероятностью качественного результата под задачу.

---

## 5. Прод-доступ с первого дня

- Новое приложение сразу имеет прод-окружение на Vercel. Тяжёлые защиты на запуске не ставим — флоу выкатки должен быть быстрым.
- **Исключение:** `/admin` всегда за простым токеном из env. Раскрывает структуру и данные — публичной быть не может.
- **Доступ агента к продукту:** логин/пароль/токены тестового пользователя лежат в env Vercel (`TEST_USER_EMAIL`, `TEST_USER_PASSWORD`, при необходимости `TEST_USER_TOKEN`). Агент сам подтягивает и сам пользуется продуктом — пользователя не дёргать.

## 6. Тестирование перед докладом

**«Собирается» ≠ «работает».** Финальное «готово» — только после реального прогона.

Флоу перед каждым докладом:

1. Определить **критерии качества** для задачи: что значит «работает».
2. Прогнать **основной сценарий** на preview-деплое (живой URL, реальный serverless).
3. Если требуется внести данные:
   - Внести через UI или API как обычный пользователь.
   - Удалить за собой по `created_at` — **только те строки, что появились в окно работы агента**.
   - Чужие/старые строки не трогать никогда.
4. Проверить **edge-кейсы** (пустые/битые данные, отсутствие ключей).
5. Только после этого — доклад + preview URL.

Что не получилось проверить — честно отметить: «не проверено: `<что>`, риск: `<где>`».

## 7. Когда агент возвращается к пользователю

Агент не беспокоит пользователя непроверенным функционалом или мелочами. Возвращается **только в двух случаях**:

1. **Архитектурный выбор** — смена стека, новая внешняя зависимость с lock-in, новая схема прав/авторизации, изменение UX Kit, новая core-таблица.
2. **Не хватает контекста** — задача допускает несколько разных интерпретаций.

В остальном — **порог 70% уверенности**: если решение кажется правильным хотя бы на 70%, агент делает сам и фиксирует как «допущение: X» в финальном отчёте.

**Агент может сам:**

- Ставить любые пакеты.
- Менять схему БД (не core).
- Писать и запускать юнит-тесты.
- Деплоить в preview, проверять, сообщать о готовности.
- Логиниться в продукт под тестовым пользователем.
- **Деплоить в прод без отдельного подтверждения** — но только если основной сценарий и edge-кейсы (раздел 6) прошли на preview. Если хотя бы один пункт не проверен — сначала спросить.

**Агент НЕ может:**

- Править эту конституцию. Может предложить правку отдельным сообщением.
- Удалять чужие или старые данные в БД.

## 8. Юнит-тесты

- Покрываем core-функционал: бизнес-логика, критические утилиты, парсеры, платёжные обработчики. UI/верстку — не обязательно.
- **Когда тест нужен — решает агент.**
- Агент сам пишет и сам запускает.
- Результаты прогонов отображаются на `/admin`: дата, что зелёное/красное, стектрейс упавших.

---

## 9. Контекстное окно

Доверяем авто-компакшену Claude Code: при приближении к лимиту платформа сама сжимает старую часть истории. Сверху агент:

- держит ответы и сообщения краткими;
- на границе крупных задач предлагает начать **новый чат** с handoff-резюме, чтобы не тащить устаревший контекст в следующую задачу.

---

## 10. Формат финального отчёта

Каждое «готово» содержит:

- **Preview URL** — ссылка на свежий деплой.
- **Что внедрено / исправлено** — короткий список изменений.
- Если это правка бага:
  - **Корень проблемы** — настоящая причина, не симптом.
  - **Что сделано, чтобы не повторилось** — гард, тест, правило, рефакторинг.
- **Что НЕ протестировано** — если есть слепые зоны.
- **Открытые допущения** — что предположил, если решал по «70%».

## 11. Мобильное приложение

- **Стек:** Swift + SwiftUI, iOS 17+. Структура проекта через XcodeGen (`mobile/project.yml`); `.xcodeproj` генерируется локально и в git **не коммитится**.
- **Расположение:** монорепо, папка `mobile/` рядом с веб. Долгоживущая ветка `mobile` для крупных мобильных фич; rebase на `main` после каждой значимой веб-фичи или раз в неделю — что наступит раньше.
- **API-контракт.** Мобильный клиент потребляет существующие `/api/*` на Vercel — отдельных «мобильных» эндпоинтов не плодим. Перед реализацией экрана: контракт (типы/форма ответа) фиксируется в `lib/api-types.ts` на `main`, потом веб и мобила реализуют каждый своё. Зеркало типов в `mobile/AIBOOSTER/Models/API.swift` держим вручную.
- **Auth:** Bearer-токен в Keychain. Сервер проверяет тот же токен, что и веб (`TEST_USER_TOKEN` для DEV-сборки).
- **Distribution:** Apple Developer Program, ad-hoc / TestFlight (закрытый круг), **не App Store**. Bundle ID согласуется отдельно. Подпись — Automatic signing в Xcode.
- **Push notifications:** через APNs. Device token регистрируется на бэкенде в таблице `device_tokens` (создаётся при первой регистрации, см. §1).
- **Не проверяется автоматически:** Swift-код компилируется только локально в Xcode на Mac. Агент пишет файлы и API, но билд + smoke-тест на устройстве — на стороне владельца. В отчётах помечать «не проверено: компиляция iOS / запуск на устройстве».
