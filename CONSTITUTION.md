# Конституция проекта AIBOOSTER

AIBOOSTER — продукт, который даёт возможность ускоренно решать многие задачи
с помощью AI в несколько шагов.

Этот документ — свод обязательных правил проекта. Он не описывает «как было бы
хорошо», а фиксирует то, что **обязательно** соблюдается любым разработчиком и
любым AI-агентом, работающим над проектом. Имена таблиц, эндпоинтов и переменных
окружения, закреплённые здесь, — **канонические и неизменные**.

---

## 1. Схема БД — без ручных шагов

### 1.1. Самопровижининг и идемпотентность
На чистой БД приложение поднимается само, без ручного SQL и ручных миграций.
Допустимы два пути:
- `CREATE TABLE IF NOT EXISTS` при первом обращении (для кэша и вспомогательных
  таблиц), либо
- миграции, запускаемые автоматически на деплое/старте.

**Ручной шаг = баг процесса.** Если для запуска на чистой БД требуется руками
выполнить SQL — это дефект, который нужно чинить, а не инструкция.

### 1.2. Один источник правды на таблицу + мягкий сбой
- Не дублируй определение таблицы. Либо ORM-схема, либо ленивый `CREATE` —
  **не оба сразу**.
- Провал создания таблицы **не валит приложение**: оборачивай в `try/catch` и
  логируй.
- Помни про права: **read-only токен БД ломает запись молча**. Проверяй права
  доступа — отсутствие ошибки не значит, что запись прошла.

## 2. Логи — единое место, известное любому чату

### 2.1. Один сток, одна форма
Все ошибки (бэкенд + клиент) пишутся в **одну** таблицу БД `app_errors`
(на serverless — только БД, файл эфемерен) в едином формате:

| Поле         | Описание                                    |
|--------------|---------------------------------------------|
| `ts`         | Время события                               |
| `level`      | Уровень (error/warn/info)                    |
| `source`     | Источник: `server` \| `client`              |
| `route`      | Маршрут/эндпоинт, где произошла ошибка       |
| `message`    | Сообщение об ошибке                          |
| `stack`      | Стектрейс                                    |
| `build`      | Версия/идентификатор сборки                  |
| `user_agent` | User-Agent клиента                          |
| `meta`       | Произвольные доп. данные (JSON)              |

### 2.2. Фиксированная точка чтения
Дамп последних ошибок отдаёт `GET /api/admin/errors?limit=N`.

Два имени — **`app_errors`** и **`/api/admin/errors`** — закреплены здесь и
неизменны. Любой агент/разработчик начинает диагностику отсюда, не спрашивая
«а где логи?».

### 2.3. Правило для сессии
При разборе бага **сначала** смотри `app_errors` / `/api/admin/errors`, чини по
стектрейсу. Пользователю отдавай понятное сообщение + `error_id` для поиска
в логе.

## 3. AI-модели — только через aimlapi.com

Все AI-модели подключаются **только** через [aimlapi.com](https://aimlapi.com) —
OpenAI-совместимый шлюз. Один ключ на все модели (GPT, Claude, Gemini,
Perplexity).

- **Не заводи** отдельные ключи OpenAI / Anthropic / Perplexity.
- Ключи: https://aimlapi.com/app/keys
- База API: `https://api.aimlapi.com/v1` (эндпоинт `/chat/completions`).

### Канонические имена env (одинаковы во всех проектах)
- `AIMLAPI_KEY` — авторизация.

## 4. Отладочная страница БД (`/admin`)

С самого старта в проекте есть **защищённая** служебная страница `/admin`
(под токеном/авторизацией, **никогда не публичная**), которая показывает:

- **Структуру БД**: таблицы и колонки с описанием на русском — что значит каждая
  таблица и поле. Описания берутся из единого реестра/комментариев схемы и
  держатся в синхроне с реальными таблицами.
- **Просмотр значений**: выбрал таблицу → постранично смотришь строки
  (read-only по умолчанию). Произвольный SQL и мутации — отдельно и тоже под
  защитой.
- **Дамп `app_errors`** — там же.

**Цель:** любой чат/агент и сам разработчик инспектируют данные и схему без
ручного SQL и без консоли БД. Диагностика начинается отсюда.

> **Важно:** страница раскрывает структуру и данные, поэтому доступ к ней —
> обязательно за авторизацией. В публичный доступ не выносить.

## 5. Сначала протестируй — потом докладывай

### 5.1. «Собирается» ≠ «работает»
Никогда не пиши «готово/работает» на основании одних лишь `tsc`/`build`.
Сначала запусти и понаблюдай реальное поведение на сценарии из задачи + на
крайних случаях.

### 5.2. Тестируй в реальных условиях (обязательно, не опция)
- Есть ключи (staging) → подними приложение и побей реальные эндпоинты.
- UI → прогони в браузере (Playwright/скриншот).
- По возможности → против preview-деплоя (настоящий serverless: таймауты,
  лимиты).

### 5.3. Что проверить нельзя — отметь честно
Нет ключа/браузера/прод-условий → **не** пиши «работает», а:
> «сделано, собирается; НЕ проверено вживую: `<что>`; вероятный риск: `<где>`»

— и попроси доступ для теста или подтверждение.

### 5.4. Мини-чек перед каждым «готово»
- [ ] Воспроизвёл основной сценарий?
- [ ] Проверил edge-кейсы и пустые/битые данные?
- [ ] Фича не падает без ключей (graceful)?

Хоть один «нет» — значит ещё **не** готово.
